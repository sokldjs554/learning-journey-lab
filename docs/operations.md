# 반복 점검 운영과 자동화

## 실제 구현

`python scripts/download.py` → 원본 SHA256 확인/보존 → `python scripts/analyze.py` → SQL 품질 규칙·마트·군집 통계·민감도·생성 장애 실습·이슈 이력 → `python scripts/build.py` → 정적 데모.

BLOCK 규칙이 하나라도 실패하면 분석 명령은 종료 코드 2, 배포 빌드는 오류로 종료한다. 차원 키 문제는 JOIN 전에 중단한다. REVIEW는 원인이 미확정인 반복 행/시점 관계이며, 주지표 선택과 한계 고지를 전제로 스냅샷을 공개한다. PASS도 '완전한 데이터'라는 뜻이 아니다. 관측 불가능한 누락은 별도 표시한다.

보고서는 날짜·랜덤 seed가 고정된 의미적 결과다. 실행 시간은 별도 파일에 두어 같은 입력의 결과 해시가 시간에 따라 달라지지 않도록 했다. 원본 자동 갱신을 허용하지 않는다. 공식 ZIP의 해시가 바뀌면 새 자료를 검토하고 manifest를 명시적으로 갱신해야 한다.

## 이슈 추적

`reports/issues.json`은 규칙 단위 등록부다. `OULAD-규칙명` ID, count, severity, status, 최초 발견 스냅샷, 값 변경 이력을 저장한다. 같은 관측을 재실행해도 중복 이력이 생기지 않는다. 0→양수는 open, 양수→0은 resolved. 처음부터 0은 clear. 이력의 snapshot은 원본 ZIP 해시다. 같은 자료에 대한 규칙 변경으로 상태가 바뀌면 git 커밋과 함께 해석해야 한다. 실제 회사 티켓이나 운영 인시던트가 아니다.

공개 자료의 미확정 이슈를 '해결 완료'로 바꾸지 않았다. 담당자가 필요한 원천 증거를 확보했을 때만 처리 정책을 확정한다.

| 규칙 | 권장 확인 주체(가상 운영 역할) | 다음 확인 |
|---|---|---|
| 일별 키/동일 값 반복 | 원천 데이터 담당 + 분석가 | 일별 여러 행의 집계 의미, 추출 SQL |
| 등록일 결측 | 등록 운영/데이터 담당 | 원천 등록 이력, 분모 정책 |
| 탈퇴 후 활동 | 제품/계측 개발자 | 탈퇴 효력 시각, 수신 지연, 접근권한 |
| 원천 누락(생성 실습) | 계측/수집 개발자 | 전송 명세, 재전송 장부, 완료 워터마크 |

## 생성 장애 실습의 범위

`source_ledger.csv`는 가상의 독립 원천 장부이며 `delivery.csv`는 의도적 장애가 포함된 수신본이다. 고정 규칙 생성이라 랜덤 seed가 필요 없다. W1 활성 10명, W2 활동 6명, 총 적격 12명. 사건 발생시각과 수신시각을 분리한다. 단위는 가상 D0 이후 초이며 실제 달력 날짜가 아니다.

- W2 1명(u5)의 이벤트 2개를 영구 제거.
- W2 1명(u6)의 이벤트 2개를 D15 수신으로 지연.
- W2 u1의 시작 행을 2회 더 수신.
- null 사용자/없는 사용자, 완료가 시작보다 빠른 세션 추가.
- 정상 발생 순서지만 역순 수신되는 세션 추가.

D14 이전 스냅샷, 정리본, D16 지연 반영본, 원천 재수집본을 비교한다. 수신 순서가 뒤집혔다는 이유만으로 정상 발생 순서를 오류로 지우지 않는다. D14 보고서의 40%는 품질 게이트가 막으며 60%를 자동 추정해 채우지 않는다. 원천 장부가 없는 실제 OULAD에서는 미수신 이벤트 개수를 알 수 없다.

## 측정한 자동화 성과

`reports/benchmark.json`에 실제 3회 전체 실행 시간, 환경, 포함 범위, 결과 해시를 기록했다. 다운로드 시간 제외, 원본 해시 검증·CSV 적재·SQL·부트스트랩·파일 생성 포함. 로컬 실행의 캐시/동시 작업 영향을 받아 일반적인 성능 보장은 아니다.

**사람의 수작업 시간, 월간 비용 절감, 회사 생산성 향상률은 측정하지 않았다.** 한 명령으로 반복 가능하다는 사실과 동일 결과 해시만 검증했다. '몇 시간→몇 초', '몇 % 절감'을 꾸며내지 않는다.

### 직접 수행할 수작업 비교 프로토콜

1. 동일 20개 규칙, 입력 스냅샷, 동일 제출물(JSON/이슈 표)을 정한다.
2. 지원자가 SQL을 한 규칙씩 실행하고 표에 기록하는 전체 시간을 잰다. 실행 대기/수동 작업/검토 시간을 분리한다.
3. 순서를 번갈아 자동 명령을 실행하며 같은 제출물을 만든다. 최초 설치와 학습 시간은 따로 잰다.
4. 각 방식 3회 이상, 누락/오입력 건수와 중앙값을 함께 보고한다. 연습 효과와 숙련 차이를 적는다.
5. 자동화 시간의 차이가 곧 분석가가 절약한 근무 시간은 아니므로 구분한다.

## CI와 배포

CI는 소규모 기준 사례·동일 생성 결과·빌드 계약을 검사한다. 전체 원본 재현은 별도 수동 workflow 또는 SQL/분석/manifest 변경 시 다운로드→전체 분석→독립 집계→일관성 검사를 실행한다. 워크플로 파일 존재와 원격 실행 성공은 별개이며 실제 실행 여부는 검증 기록에 표시한다.

공개 데모는 저장된 JSON을 브라우저에서 읽는 정적 사이트다. 브라우저 버튼이 운영 파이프라인을 실행하거나 외부 이슈를 닫지 않는다. 실제 원천 로그 수집·알림 전송·DB 접속·일정별 서비스 데이터 점검은 구현하지 않았다.

## 동일 검토표 기록 실습

[측정 절차](human-comparison-protocol.md)와 [공개 실습](https://learning-journey-lab.onrender.com/operations-practice.html)을 추가했다. 같은 OULAD 스냅샷의 3개 품질 규칙을 수동 전사하거나 자동 입력한 뒤 모두 직접 검토한다. 이는 **검토표 작성·확인**의 비교이며 전체 SQL 분석 수작업 대비가 아니다. 연습 2회와 측정 6회를 구분하고 탭 비활성·일시중지를 제외한다. 활성 구간은 집중 시간의 직접 측정이 아니다. 실제 사람의 결과 파일은 아직 수집하지 않았으므로 절감률은 없다.
