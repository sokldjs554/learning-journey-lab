이 범위를 줄여 진행하면 축소된 범위를 명시하고 '전체 프로젝트 독립 구현'이라고 기록하지 않는다. 새로운 기능을 더하는 과제가 아니며 임의로 추가 기술이나 모든 기기의 접근성 인증을 완료 조건에 붙이지 않는다. 공개 원본이 나중에 접근 불가하면 캐시·해시와 실행 범위를 기록하며 성공을 만들어내지 않는다.

## 이전 전체 구현 목표의 역할과 완료 기준

1. 지원자가 작성한 코드·테스트·실행 결과·참고 자료/도움 범위를 제출한다. 이미 본 SQL과 문서를 기억하지 못한 상태로 시험하는 과제가 아니다.
2. Codex는 환경 설정과 요구사항 설명을 돕고, 제출본을 보존한 뒤 동작·결함·근거를 검토한다. 요청에 따라 완성 코드를 제공하게 되면 해당 부분은 도움받은 구현으로 표시한다. 도움을 숨겨 독립 구현으로 인증하지 않는다.
3. 위 구성의 실행 증거, 동일 공개 입력에 대한 결과 대조 또는 차이의 정당한 설명, 연결된 UI·CI·공개 배포, 본인이 설명한 주요 설계·수정 이유를 모은다. 실제 제출 전에는 완료 표시하지 않는다.
4. 완료는 이 범위의 직접 구현 사례가 확보됐다는 뜻이다. 모든 상황의 개발 숙련도, 무도움 작성 사실, 채용 평가 결과를 인증하는 것은 아니다. 부분 완료도 각각의 직접 수행 근거로 보존한다.

## 첫 제출: 원본 검증 코드

측정용 저장소 옆의 새 작업 폴더에서 Python 파일 하나를 직접 작성한다. 예시 이름은 `validate_sources.py`이며 기존 측정 폴더의 파일은 편집하지 않는다. 환경 선택·설치는 도움을 받아도 구현 역할과 구분할 수 있다.

입력은 기존 OULAD `data/manifest.json` 파일 경로와 원본 CSV 폴더 경로다. 원본 CSV를 수정하지 않고 manifest에 기재된 7개 파일의 존재와 SHA-256을 확인한다. 모든 파일이 맞으면 각 파일의 검사 결과를 출력하고 종료 코드 0, 파일이 없거나 해시가 다르면 해당 파일과 원인을 출력하고 0이 아닌 종료 코드로 끝낸다. 원본 전체를 메모리에 한 번에 올리지 않고 읽는다. 임의 다운로드·해시 갱신·생성 자료 대체는 하지 않는다.

지원자가 함수·명령행 인자·출력 형식을 정한다. 우선 작성한 파일과 사용한 참고 자료를 제출한다. 막힌 부분은 작성한 곳까지 제출할 수 있다. Codex는 제출 전 구현 정답을 제공하지 않고 제출 후 별도 임시 파일로 정상·누락·불일치 동작을 검사한다. 이 작은 첫 모듈만으로 전체 구현 완료라고 하지 않으며, 위 표에 따라 누적한다.

## 제출 완료: 품질 SQL의 첫 세 규칙

원본 검증·DuckDB 적재 모듈을 제출했고 기능 검토를 통과했다. 아래 요구사항의 `quality.sql`을 수신했고 [16개 검사와 실제 자료 대조](applicant-quality-sql.md)를 통과했다. 아래는 제출 전 정의한 요구사항을 보존한 것이다. 기존 활동 기준 비교 SQL을 다시 작성하는 과제가 아니라 원본 행의 품질을 검사하는 연결 단계다.

출력은 `rule_id`, `issue_count` 두 열의 세 행이다. 원본과 DB 값을 수정하지 않는다. 아래 정의를 구현하고 사용한 참고 자료를 함께 보낸다.

| rule_id | 셀 대상 |
|---|---|
| registration_missing_date | studentRegistration에서 date_registration이 NULL인 행 |
| event_exact_repeat | studentVle의 code_module·code_presentation·id_student·id_site·date·sum_click이 모두 같은 행 중 첫 행을 제외한 초과 행. 같은 행 3개면 2개로 셈 |
| event_unknown_student | studentVle의 id_student가 NULL이 아닌 행 중 code_module·code_presentation·id_student 조합이 studentRegistration에 없는 활동 행. 등록의 중복 행이 검사 건수를 늘리지 않도록 함 |

SQL은 기존 전용 DB의 테이블 이름을 그대로 사용한다. 파일과 참고 자료를 제출하면 Codex가 손계산 가능한 별도 예시와 실제 자료로 검토한다. 이 세 규칙은 전체 품질 검사 구성의 첫 부분이며 모든 품질 검사를 완료했다고 표시하지 않는다.

## 제출 완료: 품질 SQL 실행·결과 저장 연결

첫 세 품질 규칙과 아래 `run_quality.py`의 제출·기능 검토를 완료했다. 아래는 제출 전에 고정한 요구사항이다. `run_quality.py`는 그 SQL을 다시 작성하지 않고 재사용하는 Python 연결 코드다. 입력 인자는 `--db`(앞서 만든 전용 DB), `--sql`(제출한 quality.sql), `--output`(결과 JSON 경로)이다.

- 기존 DB를 읽기 전용으로 열고 SQL을 실행한다. 없는 DB를 새로 만들지 않는다.
- 결과의 열은 `rule_id`, `issue_count`이며, 위 세 rule_id가 한 번씩 있고 건수는 0 이상의 정수인지 확인한다. 누락·중복·잘못된 결과는 실행 실패로 처리한다.
- `event_unknown_student`가 0보다 크면 BLOCK, 그렇지 않고 나머지 두 건수 중 양수가 있으면 REVIEW, 모두 0이면 PASS다.
- JSON에는 `scope: "first_three_rules"`, `gate`, `checks`를 저장한다. checks에는 각 `rule_id`, `issue_count`를 보존한다. 첫 세 규칙만으로 전체 20규칙 검사가 완료됐다고 표시하지 않는다.
- 성공한 검사 결과는 콘솔에도 판정과 건수를 출력한다. PASS/REVIEW는 종료 코드 0, BLOCK은 2, 파일·DB·SQL·결과 형식 오류는 1로 끝내며 오류를 성공처럼 저장하지 않는다.

이 요구사항은 실행 연결 부분이며 품질 SQL·원본·DB를 고치는 과제가 아니다. 작성한 파일과 사용한 참고 자료를 제출하면 Codex가 검사·실행·실패 상태를 검토한다.
