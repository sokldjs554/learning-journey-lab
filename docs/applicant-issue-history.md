## 통과한 범위

품질 실패·미완료·누락,20규칙 계약 위반, gate 불일치, 다른 manifest, 동일 run_id의 다른 품질 파일, 잘못된 기존 이력, 입력 경로 충돌은 기존 이력을 보존하고 오류로 끝났다. 품질 BLOCK 결과와 품질 성공 이후 다른 단계의 실패는 유효한 품질 결과로 수용했다. 원자적 저장 실패에서도 이전 파일을 보존했다.

## 수정할 한 가지: 기록된 품질 파일 해시 대조

`run()`은 quality.json의 형식과 gate를 확인한 뒤 파일 해시를 계산하지만, `run_record.json`에 이미 저장된 `artifacts["quality.json"]["sha256"]`와 비교하지 않는다. 기존 run_id의 파일 변경은 걸러도 **처음 처리하는 실행의 결과 파일 변경**은 통과한다.

실제 결과의 복사본에서 등록일 결측만45→0으로 바꿨다. 다른 review 규칙이 남아 gate는 REVIEW로 같고,20규칙 구조도 유효하다. 원래 실행 기록의 품질 파일 해시와 변경 파일 해시는 달랐지만 제출 코드는 종료0으로 처리해 기존 등록일 결측 이슈를 resolved로 바꿨다. 실제 원본·실제 실행 결과는 수정하지 않았으며, 이 현상을 실제 사용자 사고나 실제 데이터 해결로 표현하지 않는다.

| 기준 | 기대 | 실제 |
|---|---|---|
| 기록된 해시와 현재 파일 해시 | 불일치 감지 | 대조 없음 |
| 종료 코드 | 1 | 0 |
| 기존 이력 | 내용·수정 시각 보존 | 변경됨 |
| 등록일 결측 이슈 | open 유지 | resolved |

### 수정 위치와 동작

`quality_hash = digest_file(quality_path)` 다음, **이력에 적용하거나 저장하기 전**에 실행 기록에 저장된 품질 파일 SHA-256과 비교한다. 기록된 산출물 메타데이터가 있으면 그 구조·해시 형식도 검증하고, 불일치하면 `IssueHistoryError`로 종료1을 반환하며 기존 이력을 그대로 둔다.

전체 파이프라인이 품질 BLOCK으로 멈췄거나 나중 단계에서 실패한 경우에는 기존 파이프라인 계약상 최종 artifacts가 null일 수 있다. 이 경우를 무조건 오류로 바꾸지 말고, 이미 구현한 품질 단계 상태·종료 코드·20규칙·gate 검증을 유지한다. 모든 단계가 실패했는데 품질 검사가 성공했다고 가정해서는 안 된다. 최종 artifacts가 없는 실행에는 파일 바이트를 실행 기록과 대조했다는 보장을 붙이지 않는다.

기존 파일을 전부 다시 작성할 필요는 없다. 이 검사를 추가한 `update_issues.py`만 다시 제출하면 해당 결함과 관련 회귀를 확인한다. 새로운 기능이나 사람 실측은 요구하지 않는다.

## 테스트와 역할

처음에는34 passed /1 failed였다. 미해결 검사는 `strict xfail`로 명시해 저장했다. 이는 성공한 검사로 세지 않으며, 수정 후 예상 밖 성공(XPASS)은 반드시 마커 제거와 재검토를 요구한다.

문제만 실제 실패로 재현하려면 저장소 의존성이 설치된 환경에서 다음을 실행한다.

```bash
python -m pytest -q --runxfail tests/test_applicant_issue_history.py::test_recorded_quality_hash_mismatch_must_not_resolve
```

현재 제출본에서는 이 검사가 실패하는 것이 결함의 재현이다. 정상/오류 사례 전체는 다음으로 확인한다.

```bash
python -m pytest -q tests/test_applicant_issue_history.py
```

지원자는 파일을 제출했다. Codex가 검사 작성·실제 산출물 연결·복사본의 통제된 변경·문서화를 수행했고 제출 코드 로직은 수정하지 않았다. 이번 첨부에 지원자 로컬 실행 출력이 있었다고 기록하지 않는다. 이 검토는 순차 실행의 이력 관리이며 동시 작성자나 과거 실행의 시간순 재배열을 검증한 것으로 확대하지 않는다.
