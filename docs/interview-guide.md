# 프로젝트 이해와 면접 설명

이 문서는 제출용 자소서가 아니라 프로젝트 설명을 위한 참고 자료다. **기준 비교 SQL·손계산·실행·판단 실습은 완료했다.** 직접 수행 근거는 [참여 기록](participation.md)에 연결되어 있다. 아래 개념 설명과 선택 실습은 추가 완료 조건이 아니며, 프로젝트 전체 구현과 본인의 실제 수행을 구분해 설명한다.

## 90초 설명의 구조

1. 제품전략팀의 첫 업무가 데이터 운영이므로 '좋은 예측 모델'보다 '판단할 수 있는 지표'를 만드는 문제를 택했다.
2. 내부 자료는 없으므로 OULAD 공개 일별 학습 활동을 사용했다. 대학 강좌 자료이며 구독 서비스의 결제·영상 로그와 다르다.
3. 같은 일별 키와 동일 값이 반복되는 자료를 발견했다. 오류라고 단정할 원천 ID가 없어서 클릭 수 기준을 여러 정책으로 비교했다.
4. 반복 행에도 유지되는 활동일 지표로 첫 주와 다음 주의 관계를 확인하고, 개설기·다음 해·최초 활동일별로 반대 근거를 찾았다.
5. 관찰된 차이를 효과로 주장하지 않고 계측 보완→다음 학습 진입점 실험 순서를 제안했다. 별도 생성 실습으로 누락을 중복 제거만으로 복구할 수 없음을 재현했다.

숫자는 외우기 전에 `reports/findings.md`와 화면의 분모를 확인한다. '학습자 수'와 '수강 건수', '%'와 '%p'를 바꾸어 말하지 않는다.

## 완료한 기준 비교 실습 설명

아래는 지원자가 이미 제출한 계산과 판단을 Codex가 정리한 설명 예시다. 새 답변이나 재실행을 요구하는 과제가 아니다.

> 기존 프로젝트를 참고해 첫 주 활동을 1일·2일·3일 이상으로 나누는 SQL을 제출하고 실행했습니다. 가상 8행에서는 손계산과 SQL 결과를 대조했습니다. 실제 데이터에서 기준을 2일 이상에서 3일 이상으로 높이면 대상이 4,803건, 약 26.7% 줄고 재방문율은 91.7%에서 94.8%로 높아졌습니다. 제외되는 2일군에서도 3,992건이 다음 주에 활동했으므로 높은 비율만으로 기준을 바꾸는 것은 적절하지 않다고 판단했습니다. 관찰 결과이므로 활동일을 늘리는 정책의 효과라고 말할 수는 없습니다. 문제 제시·실행 안내와 코드 검토는 Codex의 도움을 받았습니다.

이 사례는 **활동 기준 변경의 타당성 검토**다. 관찰용 구분과 실제 안내 대상 선정은 다른 결정이며, 이번 분석으로 최적 안내 정책을 확정하지 않았다. 최초 과제에서 구체적인 정책 용도를 정하지 않은 것은 Codex의 과제 설계 범위이지 지원자의 미완료 사항이 아니다.

지원자가 제출한 선택란의 `사용 / 보류` 원문과 설명은 [원문 기록](../reports/applicant-threshold-analysis.json)에 보존한다. 위 예시는 실제로 제출한 이유를 정리한 것이며 새로운 직접 발언으로 기록하지 않는다.

## 쉬운 말로 설명하기

| 개념 | 쉬운 설명 | 이 프로젝트에서 필요한 이유 |
|---|---|---|
| 복합키 | 사람 번호 하나가 아니라 강좌·개설기까지 묶은 주소 | 같은 사람이 여러 강좌를 들을 수 있음 |
| 데이터 계약 | 어떤 값을 어떤 의미로 기록할지 정한 약속 | 1행을 이벤트 1개로 오해하면 지표가 바뀜 |
| 분모 | 비율을 계산할 때 기준으로 삼는 전체 | 활동자만 보고 전체 신규 수강생인 것처럼 말하면 선택 편향 |
| 멱등성 | 같은 입력을 다시 처리해도 결과가 늘거나 달라지지 않음 | 중복 이슈와 반복 집계 방지 |
| 워터마크 | 어느 시점까지 들어온 데이터를 보고서를 낼 만큼 기다렸는지 정한 마감 | 늦게 온 로그를 이탈로 오인하지 않기 |
| 군집 부트스트랩 | 한 사람의 여러 수강을 묶어 사람 단위로 다시 뽑아 보기 | 같은 사람의 기록을 독립 사람처럼 세지 않기 |
| 선택 편향 | 자주 온 사람이 원래 의욕이 더 높았을 수 있음 | 두 번 오게 하면 재방문이 같은 폭으로 늘어난다고 말할 수 없음 |
| ITT | 실험에 배정된 모두를 처음 배정대로 비교 | 실제 화면을 본 사람만 고르면 랜덤 배정 이점이 사라짐 |
| MDE | 이번 실험 규모로 찾아내려는 최소 차이 | 가정한 +3%p는 얻을 성과가 아니라 설계 입력 |

## 예상 질문과 답의 핵심

**왜 OULAD인가?** 라이선스 명확·공식 파일 확보·등록/자료/활동 관계로 SQL 검증 가능. 대신 시청 시간과 구독 갱신은 없다. EdNet KT4는 이후 2,048명·854,678행의 보조 자료로 추가했다. 개별 행동·구매·환불 기록은 있으나 관측 종료·가입일·가격·갱신 상태가 없어 구독 유지나 매출을 계산하지 않는다. OULAD와 합산하지 않는다. [추가 분석](ednet-analysis.md).

**반복 행을 왜 제거하지 않았나?** 이벤트 ID가 없다. 여러 번 접근한 일별 묶음일 수도 있다. 동일 값 제거·자료별 최대값을 진실로 지정하지 않고 분류 변경을 측정했다. 활동일 지표는 존재 여부라 이 모호함에 덜 민감하다.

**SQL과 Python을 왜 나눴나?** SQL은 복합키·JOIN·집계·품질 조건을 리뷰하기 좋다. Python은 다운로드 검증·실행 순서·통계 재추출·보고서 생성·테스트를 묶는다. DuckDB는 별도 서버 없이 1천만 행 CSV를 SQL로 다룰 수 있다.

**차이가 유의하니 바로 배포하면 안 되나?** 재방문하기 쉬운 사람의 자기선택과 강좌 일정이 남는다. 통계 구간은 교란을 제거하지 않는다. 다음 해에서도 같은 방향이라는 사실과 인과효과는 다르다.

**첫날 콘텐츠 접촉 가설은?** 전체에 작은 양의 연관성이 있지만 일부 개설기는 반대, 2013 탐색 구간은 0 포함. 큰 폭의 콘텐츠 노출 확대 결론을 보류했다. 불리한 결과도 의사결정 자료다.

**누락은 어떻게 검출했나?** 공개 데이터에서는 검출할 수 없는 범위를 명시했다. 생성 실습에서만 독립 원천 전송 명세와 대조했다. 없는 이벤트를 만들어 채운 게 아니라 지연 도착과 원천 재전송을 구분했다.

**왜 DiD/DoubleML/SHAP/Markov를 안 썼나?** 처치·통제·교란 통제·전이 안정성 등 필요한 조건이 없다. 방법론 이름을 추가하면 설명만 복잡해지고 인과 근거는 생기지 않는다. SHAP은 모델 설명이며 자동 인과 추론이 아니다.

**자동화로 얼마나 절약했나?** 같은 품질 규칙 3개의 검토표 기록·대조를 지원자 1명이 각 방식 3회 수행했다. 작업 구간 중앙값은 수동 A 40.27초, 자동 채움 B 14.20초로 B가 26.06초 짧게 관측됐다. 양쪽 모두 오류·누락·미확인 0건이다. 안내·학습·고정 순서·중간 코드 실습의 영향을 분리할 수 없어 일반적인 생산성 개선이나 오류 감소로 주장하지 않는다. [실측 결과](human-comparison-results.md). 후속으로 전체 OULAD의 단계별 실행·직접 기록과 일괄 실행·자동 채움을 1명이 비교했다. 완료 6회·무효 5회를 모두 보존했으며 손계산·독립 코드 작성 시간은 아니다. [v1 전체 운영 결과·재시작 부담](full-operations-human-results.md). 이어 개선된 v2도 본 측정 6회를 완료했다. 본 측정 중단을 포함한 경과 합계는 A 1,426.62초/B 356.57초다. [v2 사람 실측 결과](full-operations-v2-human-results.md). 기존 측정과 반복 학습의 영향을 분리하지 못하므로 v1 대비 개선 효과로 해석하지 않는다.

**테스트가 코드를 그대로 복사한 건 아닌가?** 6명 SQL 기준 사례와 12명 장애 장부는 손계산 가능하다. 전체 29,671 수강 건은 다른 라이브러리·연산 순서로 작성한 pandas 집계와 대조했다. 두 구현이 같은 원본의 의미 한계를 해결하는 것은 아니다.

**클래스101에서 무엇을 추가로 알아야 하나?** 실제 첫 학습/재개 흐름, 콘텐츠 권한, 구독·결제 주체, 기기·재생 오류, 신규 첫 학습 시각, 실험 배정·노출, 학습 목적. 인터뷰와 실제 사용 관찰도 필요하다.

## 선택 참고 실습

초기 안내를 참고용으로 보존한다. 아래 여덟 항목을 모두 수행해야 완료되는 체크리스트가 아니며, 이미 완료한 세 단계 실습을 다시 할 필요가 없다. 새로 수행하지 않은 항목은 경험으로 주장하지 않는다.

1. README대로 clone→설치→테스트. `tests/conftest.py`의 학습자 1/2/6 결과를 종이에 계산한다. day6/7/13/14 경계를 설명한다.
2. `data/synthetic/source_ledger.csv`와 `delivery.csv`에서 u5/u6/u1을 찾는다. 왜 60%·40%·50%가 나오는지 표를 그린다.
3. `python scripts/download.py` 후 전체 분석과 독립 대조 실행. 해시와 0 mismatch를 확인한다.
4. `sql/quality.sql`의 규칙 하나를 직접 설명한다. `sql/dimensions.sql`을 제거했을 때 존재하지 않는 개설기가 어떻게 사라지는지 테스트로 확인한다.
5. 공개 화면에서 AAA 2014J 또는 BBB 2014J를 선택하고 첫날 콘텐츠 접촉의 반대 방향을 읽는다. '추천이 나쁘다'고 결론낼 수 없는 이유를 말한다.
6. 임계값 10→20의 민감도 표와 활동일 지표가 다른 이유를 설명한다.
7. 신규 기능을 추가하지 말고, 한 규칙/테스트/문서를 스스로 수정하고 자신의 커밋을 남긴다. 이해하지 못한 코드와 AI 도움을 기록한다.
8. 실제 서비스의 허용된 화면을 직접 관찰하고 인터뷰 질문을 작성한다. 이 단계의 관찰을 이번 프로젝트에 이미 수행한 것처럼 소급하지 않는다.

## 참여 구분 체크리스트

초기의 빈 자기점검 양식은 실제 참여 상태를 나타내지 못하므로 아래 근거별 기록으로 대체했다. 전체 기술 숙련을 일괄 인증하는 표가 아니다.

| 설명할 내용 | 확인된 범위 | 근거 |
|---|---|---|
| 직접 실행·확인 | 로컬 분석·독립 대조 출력, CI 확인, 직접 비교 실측 | [참여 기록](participation.md) |
| SQL의 분자·분모와 집계 | 세 집단 SQL과 실제 출력, 가상 8행 손계산 대조 | [기준 비교 실습](applicant-threshold-analysis.md) |
| 결과와 판단 | 대상 감소·재방문율 차이·제외 집단 재방문을 고려한 이유 | [제출 원문](../reports/applicant-threshold-analysis.json) |
| 결과의 한계 | 학습 의지·강좌 특성 등 교란과 인과 해석 한계 설명 | 같은 제출 원문 |
| 구현과 도움의 구분 | 지원자 제출·직접 수행과 Codex의 안내·구현·검증·커밋을 별도 기록 | [역할 구분](participation.md) |

새로 입증되지 않은 JOIN 설계나 모든 통계 기법의 숙련을 이 결과에 포함하지 않는다. 이미 확인한 SQL·검증·판단 경험은 그대로 인정한다. 실제 회사 적용·갱신 성과는 없으며, 데모 참여자 피드백과 구분한다.
