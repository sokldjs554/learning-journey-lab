# 남은 검증의 실제 진행 절차

출발 소스: `73cbdb387eba3b7723e7f974b38748f3bf949cf3`. 절차를 준비한 것과 실제 사람이 수행한 결과를 구분한다. 사용자는 맥북·안드로이드, Python·SQL 설치와 실행 경험을 보고했다. 이후 직접 CI 화면 확인과 Safari 16.6.1·Samsung Internet 30.0.5.27·VoiceOver의 제한된 과제 결과를 받았다. [직접 기기 확인 결과](device-check-results.md). 2026-10-31에는 Python 3.14 맥북의 다운로드·분석·독립 대조·일치 검사 출력도 받았다([직접 참여](participation.md)). 정확한 Python 패치 버전과 내려받은 ZIP의 소스 커밋은 미확인이다. 회사 권한의 획득 방법을 질문했으므로 승인·접근이 확보됐다고 기록하지 않는다. 이 문서를 작성했다고 아래 항목을 완료로 바꾸지 않는다.

## 1. 직접 추가한 테스트 확인

`verify`는 여러 검증 단계를 묶은 GitHub Actions 작업 이름이다. 그 안의 `Run python -m pytest -q`는 Python으로 pytest 테스트 검사기를 실행하는 단계다. `Run python scripts/verify.py`는 별도의 보고서 일관성 검사다.

1. [테스트 작업 화면 직접 열기](https://github.com/sokldjs554/learning-journey-lab/actions/runs/41011751113/job/123918957666).
2. 가운데 단계 목록에서 **Run python -m pytest -q**를 찾는다. `Set up Python`이나 `Run python scripts/verify.py`와 구분한다.
3. 단계 이름을 눌러 로그를 펼친다. 이미 펼쳐져 있으면 마지막 줄까지 읽는다.
4. 이 실행의 실제 마지막 결과는 `30 passed in 1.19s`다. Codex가 원격 로그에서 확인한 값이다. 이후 사용자가 이 단계 안내를 받고 결과가 표시됨을 확인했다. 실습 브랜치 당시 테스트는 30개이고 이후 통합된 프로젝트의 115개와 시점·코드 범위가 다르다.
5. 사용자가 실제로 읽은 결과를 전달한다. 열지 못하면 표시되는 화면이나 오류를 그대로 알려 준다.

[추가한 테스트](../tests/test_user_repeat.py)는 [기준 자료](../tests/conftest.py)에 동일한 행이 이미 2개 있는 상태에서 같은 행을 1개 더 넣는다. 동일 행 3개 중 하나만 남겨 세면 반복 초과는 `3−1=2`개다. 사용자는 반복 초과 행 수라는 의미를 설명했으며, 이 계산·fixture 설명은 Codex가 추가로 안내했다. 독립 설계·무도움 설명으로 기록하지 않는다. CI 화면 직접 확인은 사용자 응답으로 완료 기록했으며 새로운 CI 실행과 구분한다.

## 2. 실제 기기와 보조 기술

아래는 전체 절차이며 전부 수행했다는 뜻은 아니다. 현재 받은 결과는 [Safari·Android·VoiceOver 기록](device-check-results.md)을 따른다. 미확인 범위도 해당 문서에 남겼다.

먼저 사용할 노트북 OS, 휴대폰 종류, 브라우저·버전을 확인한다. 실제 장치 없이 Playwright의 화면 크기만 바꾸는 검사를 추가 수행하지 않는다. Safari는 Apple 기기의 실제 Safari에서 확인해야 한다.

각 장치에서 [공개 데모](https://learning-journey-lab.onrender.com)를 열고 다음을 확인한다. 이는 수치·조작 QA이며 정답을 미리 알려 주지 않는 사용성 과제와 구분한다.

1. 지표 검토에서 동일값 반복을 열고 지표 영향으로 이동한다. 369건 설명이 잘리거나 가려지는지, 목록으로 돌아갈 수 있는지 확인한다.
2. 재방문 근거에서 전체 범위의 분자 20,303·분모 23,522·86.3%를 읽는다. BBB·2014J로 전환해 같은 범위의 지표가 바뀌고 콘텐츠 차이 −6.6%p가 표시되는지 확인한다.
3. 검증 계획으로 이동해 제목과 현재 상태를 읽는다. 작은 화면에서 확대·스크롤·선택 상자를 실제로 조작한다. 상세 기술용 표의 가로 스크롤과 페이지 전체가 뜻하지 않게 밀리는 현상을 구분한다.
4. 실제 화면 읽기 도구를 사용할 수 있으면 본문 바로가기, 화면별 제목, 범위 선택 상자의 이름·현재 값, 분자·분모, 키보드 초점을 확인한다. Windows 내레이터/NVDA, macOS·iPhone VoiceOver, Android TalkBack 중 실제 사용한 이름·버전을 적는다. 처음 쓰는 사람이 안내받은 QA와 숙련된 보조 기술 사용자의 검토를 구분한다.

기록 항목: 실제 장치·OS·브라우저·보조 기술, 수행한 번호, 실제 관찰, 도움, 실패·중단 이유. 보조 기술을 켜기 전 종료 방법부터 안내한다. 장치 종류가 확인되면 그 환경의 조작 방법을 한 단계씩 제공한다. 존재하지 않는 장치나 설치된 프로그램을 가정하지 않는다.

## 3. 전체 분석 작업의 사람 기준선

**전체 분석의 사람 수작업 기준선은 아직 측정하지 않았다.** 별도로 기존 자동화 명령 재실행·세 결과 확인을 1회 계측해 총 100초로 보고받았다([결과·해석 한계](local-rerun-results.md)). 아래 전체 수작업 비교 조건을 완료했다는 뜻은 아니다. 기존 3개 규칙 검토표 실측과 별도다. 맥북에서 안내받은 실행 연습은 완료했고 결과 해시는 기존 보고서와 일치했다. 출력의 78.098초는 단일 분석 명령의 실행 시간이며 사람 기준선이 아니다. 사람이 전체 분석을 수행할 준비가 됐는지부터 확인한다. 설치·다운로드·처음 배우는 시간은 반복 업무의 실행 시간에 섞지 않는다. OULAD 원본 CSV는 manifest 합계 464,401,476바이트(약 442.9MiB)이며 압축 파일·작업 DB·설치 공간은 추가로 필요하다.

먼저 사용자의 OS와 Python·SQL 실행 가능 여부를 확인한다. 준비 후 다음 작업을 연습하고 산출물을 맞춘다.

| 비교 작업에 포함할 범위 | 동일 결과를 확인할 근거 |
|---|---|
| 동일 원본 해시 확인·자료 적재 | `data/manifest.json`의 7개 CSV 해시 |
| 품질 규칙 20개 실행·판정 | `sql/quality.sql`, `sql/dimensions.sql`, BLOCK/REVIEW 구분 |
| 적격 등록·시간 창·마트·반복 처리 및 탈퇴 민감도 | `sql/marts.sql`, 등록 단위 키·제외·D0/6/7/13/14 경계 |
| 전체·개설기·시점 분리·최초 활동일·통계 재추출 | `scripts/analyze.py`, `src/journey/statistics.py`, 동일 seed·재추출 횟수 |
| 생성 장부·이슈 이력·결과 출력 | `src/journey/faults.py`, `src/journey/tracker.py`, `reports/report.json`, `reports/issues.json` |
| 결과 검토 | 독립 대조·보고서 해시·기존 이슈 이력 보존. 검토를 한 방식에서만 생략하지 않음 |

사람이 단계별로 SQL·Python을 실행하고 검토하는 작업과 통합 명령으로 같은 산출물을 만드는 작업을 비교할 수 있다. 이때 측정 대상은 **기존 분석을 다시 실행·검토하는 작업**이다. 처음부터 분석을 설계하거나 코드를 독립 작성하는 시간, 사람이 계산기를 사용해 부트스트랩을 계산하는 시간이라고 표현하지 않는다. 같은 명령의 단순 클릭 횟수만 달리한다면 명령 조작 시간으로 범위를 더 좁혀야 한다.

준비가 되면 같은 입력·검토 수준으로 각 방식 연습 후 측정한다. 시작·종료, 실행 대기, 수동 조작·검토, 도움·중단·제외 구간, 오류·누락·산출물을 남긴다. 순서·횟수는 측정 전에 정하고 실제로 수행한 회차만 기록한다. 서로 다른 환경이나 과거의 기계 실행 중앙값을 새 사람 시간과 직접 빼지 않는다. Codex의 작업 시간은 사람 기준선으로 사용하지 않는다.

전체 작업을 이해하고 수행하기 어렵다면 학습을 먼저 진행한다. 20개 규칙이나 명령 실행 일부만 수행하고 전체 분석 기준선을 완료했다고 쓰지 않는다. 실제 작업 기록과 동일 결과를 확보한 뒤에만 측정 결과 문서를 작성한다.

## 4. CLASS101 실제 서비스 실험·사업 결과

현재 회사 서비스에 배포하거나 로그를 읽을 수 있는 접근 수단이 연결되어 있지 않다. 사용자에게 승인과 접근 범위를 확인 요청했으며 답변 전에는 운영 접근이 있다고 가정하지 않는다. 비밀번호·원본 고객 데이터를 채팅으로 요청하지 않는다.

권한이 있다면 승인된 시스템 안에서 현행 학습 종료 화면, 기능 중복, 배정 원장, 유효 학습·결제·환불·권한의 정의, 관측 종료 보증을 먼저 확인한다. 기존 [실험 설계](experiment-plan.md)와 [입력 검사](experiment-readiness.md)에 실제 필드·기준율·유입·최소 의미 차이·중단 기준을 대조한다. 결제 금액·갱신·권한 이력이 없으면 재방문 검사만으로 매출·갱신 성과를 산출하지 않는다.

권한이 없으면 실제 CLASS101 실험은 실행할 수 없다. 준비된 설계나 합성 검사를 다시 실행한 일을 실제 서비스 실험으로 바꾸어 기록하지 않는다. 데모를 본 참여자 1명을 회사 서비스 A/B 실험의 참여자로 세지 않는다.

실제 실험을 시작하더라도 배정·모집 후 최소 관측 창과 수신 유예가 끝나야 판정할 수 있다. 현재 설계는 마지막 배정 뒤 14일 관측과 사전에 합의한 지연 유예를 요구한다. 모집 기간과 장기 갱신 관찰은 추가로 필요하므로 지금 턴에 사업 성과까지 완료했다고 선언할 수 없다.

## 실제 회사 접근을 문의하는 경로

2026-10-30 공식 [채용 문의 안내](https://help.class101.tv/classmate/class101-recruitment-inquiry)에서 확인한 일반 채용 문의 주소는 **recruit@101.inc**다. 이 주소는 문의 창구이며 데이터 접근·실험 실행 승인을 자동 부여하는 경로가 아니다. 외부 지원자에게 내부 데이터나 실험 환경을 제공하는 프로그램은 확인하지 못했다.

문의한다면 지원자에게 제공 가능한 공개/비식별 예제 자료 또는 별도 테스트 환경이 있는지부터 확인한다. 제공 가능하다는 답변을 받은 경우 회사가 지정한 담당자에게 사용 목적·허용 데이터·보관·결과 공개 범위를 확인한다. 실제 서비스 화면 변경·사용자 배정·결제 분석 권한은 별도로 명시되어야 하며, 일반 계정이나 샘플 데이터 제공만으로 그런 권한이 생기지 않는다. 구체적인 회사 내부 승인 절차는 공개 자료로 확인하지 못했다.

현재 [공고](https://jobs.class101.net/job_posting/Yhpgrtd3)에는 지원 전에 CLASS101 운영 데이터 접근이나 실제 A/B 실험 실행을 요구하는 항목이 없다. 지원 준비를 위해 이 권한 확보를 필수 완료 조건으로 삼지 않는다. 회사의 별도 승인과 실행 환경이 없으면 실제 서비스 실험은 프로젝트의 명시된 한계로 유지한다. Codex는 회사에 연락하거나 메시지를 발송하지 않았다.
