# UI 재조사 — 공고의 업무와 화면 구조 대조

조사일: 2026-10-29, 한국 시간. 대상: 배포 버전 `26bbc67f54171f7fb12e53492341a1c3643b593c`.
상태: 조사와 개편 제안. **아래 문제는 발견 사항이며 UI 수정 완료 기록이 아니다.**

## 결론

기존 화면은 소개용 대시보드의 구조다. 큰 제목, 설명, KPI, 차트, 긴 섹션 순서가 중심이고 사용자가 검토할 항목과 근거는 뒤에 있다. 색이나 둥근 모서리를 바꾸는 것으로 해결되지 않는다. 공고의 데이터 운영→자동화→분석·액션 흐름을 화면의 작업 단위로 옮겨야 한다.

초기 구현은 '채팅·그라데이션을 피하기'에 집중했지만, 실제 분석가의 검토 흐름을 구현하는 기준이 부족했다. 기존 기능·접근성 테스트 통과는 이 정보 구조의 적합성을 입증하지 않는다. 이번 사용자 지적을 디자인 피드백으로 기록하며 실제 CLASS101 직원의 사용성 평가로 해석하지 않는다.

## 공고와 화면의 간극

[공고 전문](https://jobs.class101.net/job_posting/Yhpgrtd3)을 다시 직접 열람했다. 제품전략팀 DA이며, 운영부터 출발하는 직무다. 공고는 특정 UI를 요구하지 않는다. 아래 화면 요구는 공고와 프로젝트 데이터를 대조한 설계자의 해석이다.

| 직무 요구 | 현재 화면 | 필요한 변화 |
|---|---|---|
| 로그 품질·정합성 관리 | 품질 규칙은 두 번째 긴 섹션, 20개 접기 목록 | 검토가 필요한 항목부터 선택하고 조건·관측값·판단 영향을 함께 확인 |
| 반복 업무 자동화 | 자동화는 주로 코드와 문서에 존재 | 실제 실행 결과·동일 입력 재현·남은 이슈를 화면에서 추적 |
| 원인 파악과 개선 | 규칙 건수와 외부 SQL 링크 | 규칙별 정확한 SQL, 영향 지표, 가능한 조치와 미확정 이유 연결 |
| 가설→실행→피드백 | 결과·반례·다음 액션이 멀리 분산 | 하나의 가설 안에서 근거·반례·수정된 판단을 비교 |
| SQL·통계·개발 이해 | 숫자는 있지만 계산 조건을 열어 읽어야 함 | 분모·시간 창·처리 정책을 비교 화면 옆에 지속 표시 |
| 구독·콘텐츠 전략 | 대학 자료의 재방문 분석 중심 | 서비스에 옮길 수 있는 가설과 옮길 수 없는 결제·갱신 판단을 구분 |

## 실제 화면 측정과 코드 확인

Chromium, 1440×1000 및 390×844에서 공개 데모를 직접 열었다. 아래 값은 해당 조건의 문서 좌표이며 모든 기기의 보편값이나 사용자의 완료 시간을 뜻하지 않는다. 측정 데이터: [ui-audit.json](../../reports/ui-audit.json).

| 발견 | 근거 | 판단 |
|---|---|---|
| 첫 화면을 제목과 소개가 차지 | PC 품질 섹션 y=1,168.7px. 모바일 첫 숫자 y=827.6px, 품질 섹션 y=1,524.8px | 첫 업무의 대상이 늦게 등장. 모바일에서는 첫 숫자도 화면 하단에 걸림 |
| 하나의 긴 페이지 | PC 높이 7,072px, 모바일 8,169px, 접힌 상세의 초기 상태 | 작업별 왕복과 비교에 불리하다는 휴리스틱 판단. 읽기 시간은 미측정 |
| 범위 선택과 전체 근거가 혼재 | AAA 2014J 선택 시 요약·활동일 차트만 변경. 시간 재확인·콘텐츠 반례는 전체 기준 유지 | 계산 오류로 단정하지 않음. 전체 기준 문구는 존재하나 사용자가 범위를 계속 구분해야 함 |
| 공유할 수 없는 선택 상태 | 개설기 선택 후 URL 동일, 새로고침 시 all 복원 | 검토하던 조건을 링크로 전달할 수 없음 |
| 현재 위치 표시 부재 | nav의 aria-current 0개, 메뉴는 섹션 앵커 | 메뉴가 작업 탐색보다 보고서 목차로 기능 |
| 이슈 이력 연결 부재 | web/app.js는 report.json만 로드. reports/issues.json의 상태·이력은 미표시 | 이미 구현한 운영 자동화의 증거가 데모에 드러나지 않음 |
| 모든 검증 SQL 링크가 같은 파일 | 20개 모두 sql/quality.sql. 이 중 6개 정의는 sql/dimensions.sql에만 존재 | 실제 근거 연결 결함. 개편 때 규칙→파일 매핑부터 수정 필요 |
| 건수만으로 규칙 정렬 | count 내림차순, 0건 통과까지 동일한 목록 | 영향과 심각도보다 큰 수가 우선. 서로 겹치는 반복 행 건수를 합칠 위험도 별도 고지 필요 |
| 실패·수정 과정의 노출 부족 | docs/learning-log.md는 있으나 주 흐름에서 개별 판단과 연결되지 않음 | 공고가 강조한 피드백과 개선이 화면에서 약함 |

측정 스크립트의 첫 시도에서 닫힌 details 내부의 innerText가 빈 문자열이었다. textContent로 바꿔 다시 추출하고 SQL 원문과 대조해 6개 링크를 확정했다. 숨겨진 오류 상태 h1을 잘못 선택한 제목 높이 값은 분석에서 폐기했다.

## 조사한 제품과 디자인 체계

9개 제품군과 2개 디자인 체계를 조사했다. 공식 문서의 워크플로와 공개 제품 이미지에 한정했다. 유료 계정에 로그인해 제품을 직접 운영한 것은 아니다. **이미지까지 시각 확인한 제품은 Segment·Statsig·Metabase·GX**다. 나머지는 공식 설명을 읽은 근거이며 시각 검증으로 부풀리지 않는다.

| 공식 자료 | 직접 확인한 내용 | 채택할 원리 | 그대로 가져오지 않을 것 |
|---|---|---|---|
| [Amplitude Observe](https://amplitude.com/docs/data/validate-events) | 계획된 스키마와 실제 이벤트의 상태 구분 | 기대 조건과 관측값을 함께 제시 | 실시간 이벤트 수집, SaaS의 설정 메뉴 전체 |

| [Statsig Diagnostics](https://docs.statsig.com/experiments/monitor) | 건강 상태 목록과 선택된 검사의 설명을 함께 표시한 이미지 | 목록+선택 상세, 결과 해석 전 신뢰 조건 | 실제 실험이 없는 프로젝트에 정상 실험 상태 표시 |

| [Metabase Drill-through](https://www.metabase.com/docs/latest/questions/visualizations/drill-through) | 차트 선택에서 해당 값·행·세분화로 이동하는 공식 이미지 | 숫자를 근거로 이동하는 진입점으로 사용 | 집계 파일만 있는데 원본 조회가 가능한 것처럼 표시 |
| [Carbon Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) | 검색·정렬·행 확장·도구 모음과 표의 배치 원칙 | 검토 항목 탐색과 필요한 상세만 확장 | 읽기 어려운 초고밀도, 쓸모없는 체크박스·일괄 실행 |
| [GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/) | 남은 일과 상태의 구분. 순서가 고정된 흐름에는 부적합하다는 조건 | 사용 목적에 맞을 때만 상태 목록 채택 | 모든 단계를 무조건 체크리스트·칸반으로 바꾸기 |

핵심은 카드나 사이드바의 금지가 아니다. 실제 도구에도 둘 다 있다. **화면 요소가 사용자의 검토 대상과 다음 행동에 묶이는지**가 차이다. 타사 스크린샷은 시각 분석에만 사용했고 저장소에 재배포하지 않는다.

## 비교한 개편 방향

| 방향 | 장점 | 이 프로젝트의 약점 | 판단 |
|---|---|---|---|
| 짧은 분석 보고서 | 면접관이 처음 읽기 쉽고 결론 전달에 강함 | 운영 자동화와 검토 행동이 계속 문서 뒤에 남음 | 소개 문서에서 사용 |
| 검토 항목 중심 작업 화면 | 품질 문제→지표 영향→판단을 한 흐름에서 탐색 | 용어와 밀도를 조절하지 않으면 낯선 사람이 어려움 | 추천. 목적 한 줄·현재 판단을 작게 고정 |
| 실험 결과 작업 화면 | 가설과 검증 계획을 비교하기 좋음 | 실제 실험이 없어 성과가 있는 듯 오해하기 쉬움 | 실험 설계 하위 화면에만 사용 |

추천은 설계자의 제안이며 사용자가 이 레이아웃을 승인했다고 기록하지 않는다. 이번 요청의 범위는 조사다. 새 제품 코드나 UI 개편은 이 문서에 포함하지 않는다.

## 추천 구조: 검토 항목에서 판단까지

첫 화면 제목 후보는 **학습 지표 검토**. 한 줄 목적은 '첫 주 학습 신호를 재방문 실험에 사용할 수 있는지 검토'. OULAD·2013–2014·공개 스냅샷과 실제/생성 구분은 상단에 유지한다.

1. 현재 판단을 짧게 표시: 활동일 사용 / 클릭 기준 보류. 바로 아래 검토 항목을 제시.
2. 검토 목록: 항목, 상태, 영향을 받는 지표, 다음 검토. 원인 미확정을 오류 확정과 구분.
3. 선택 상세: 관측 근거·정확한 SQL / 지표 영향 / 판단과 수정 기록. 긴 설명은 해당 항목에 귀속.
4. 재방문 근거: 선택한 개설기·기간의 표와 차트를 동기화. 전체 분석은 별도 범위로 분명히 분리.
5. 실험 설계: 계측 선행조건, 실제 미실행 상태, 필요한 추가 자료. 표본 계산은 보조 상세.
6. 생성 로그 실습은 별도 경로·배지로 제공. 실제 운영 사례와 섞지 않음.

예시 검토 항목(새 숫자 아님):

| 항목 | 상태 | 확인된 영향 | 다음 행동 |
|---|---|---|---|
| 동일 값 반복 | 원인 미확정 | 10클릭 기준 369수강 건 분류 변경 | 처리 정책 비교 |
| 탈퇴 이후 활동 | 해석 필요 | 등록 기간 정책에 따른 지표 민감도 존재 | 포함/제외 근거 비교 |
| 콘텐츠 접촉 가설 | 우선순위 보류 | 22개 개설기 중 9개 반대 방향 | 반례 상세 |

반복 행 규칙 사이에는 겹침이 있다. 검토 항목 수·행 수·수강 건수는 같은 단위로 합산하지 않는다. `first_seen`은 현재 코드에서 원본 스냅샷 해시이며 실제 장애 발생 시각이 아니다. 이를 날짜나 운영 기간으로 꾸미지 않는다.

## 시각·상호작용 기준

- 대형 홍보 제목과 영문 장식 라벨을 줄이고 현재 작업명·대상·상태에 공간 배정.
- 수치를 모두 큰 KPI로 만들지 않음. 건수·단위·조건을 해당 검토 항목 옆에 배치.
- 색은 검토 필요·차단·선택 상태에 제한. 상관관계의 양수를 녹색 성공으로 과장하지 않음.
- 한국어 주 레이블, 실제 SQL 식별자는 보조로 표시. 상태는 색뿐 아니라 글자로 구분.
- 기본 표 행은 읽을 수 있는 밀도부터 시작. 작은 글씨로 밀어 넣지 않음. 클릭 영역과 초점 유지.
- PC는 목록과 선택 상세의 비교를 우선. 모바일은 목록→상세→뒤로 구조로, 전체 긴 페이지 축소를 피함.
- 개설기·검토 항목을 URL에 반영해 새로고침·뒤로가기·공유가 같은 근거로 돌아오게 함.
- 버튼은 실제 가능한 동작만 제공: 저장된 근거 보기, 정확한 SQL 열기, 정책 비교. 실행 서버가 없으면 '점검 실행' 버튼을 만들지 않음.
- 가짜 담당자·실시간 표시·해결 처리·알림·처리 속도 개선률을 넣지 않음.

## 개편 후 확인할 과제

아래는 앞으로 측정할 기준이며 달성 결과가 아니다.

- 1440×900 및 390×844 첫 화면에서 목적·출처·현재 판단·다음 검토 진입점을 확인.
- 동일 값 반복 항목에서 369건의 정의와 정책 비교 근거로 연결.
- 20개 규칙의 파일 경로·조건·건수 일치, 특히 dimensions의 6개 링크 확인.
- 선택 범위에서 표·차트·설명 일치. 전역 근거를 부분 집단 결과로 오해할 구조 제거.
- URL 복원, 뒤로가기, 키보드 목록/상세 이동, 모바일 상세 복귀 검증.
- REVIEW/미검증/실행 실패/BLOCK/정상 0건/검색 0건을 서로 다른 상태로 처리.
- 실제 없는 이력·실험·운영 기능이 표시되지 않는지 점검.
- 사용자 검토 시 '문제가 무엇인지, 왜 이 지표인지, 무엇을 해야 하는지'를 설명 가능한지 확인. 아직 사용자 테스트 시간·성공률은 없음.

## 조사 한계

CLASS101 내부 분석 도구의 화면은 확인할 수 없으며 그들이 어떤 UI를 사용한다고 주장하지 않는다. 공식 제품 문서의 예시는 실제 사용성 비교 실험이 아니다. 이번에는 연구 결과와 기존 UI 결함을 기록했으며, 발견한 링크 결함을 포함한 화면 개편은 아직 적용되지 않았다.
